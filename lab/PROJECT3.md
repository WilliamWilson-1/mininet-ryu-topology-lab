# Project 3 · 负载均衡实验

Ryu 为 10 条并发 UDP 流计算最短路基线和负载均衡方案。两轮使用同一批源主机、目的主机、目标速率和端口。交换机间链路每个方向的名义容量是 10 Mbps。

## 启动

在 Ubuntu 克隆分支，按 [实验手册](README.md) 安装 Ryu 4.34、Mininet 和 OVS，并在下方克隆的目录中配置虚拟环境。打开两个终端，在同一个仓库的 `lab` 目录启动 Ryu 与 Mininet。补装 iperf3。

```bash
git clone --branch project3-DLC --single-branch \
  https://github.com/WilliamWilson-1/mininet-ryu-topology-lab.git ~/mininet-project3-dlc
sudo apt install iperf3
```

默认使用 4×5 网格。待交换机、主机和链路发现完成，从 Ryu 的真实页面进入「负载均衡」，选择种子，点击「计算方案」。页面显示基线和优化的 62 个有向链路利用率，以及 10 条流在两种方案下的路径。

种子 17 在默认网格上的计划峰值为 180% 和 90%。这些百分比由发送需求计算，用于定位过载链路。超过 100% 表示该方向的计划速率大于容量。

## 连续跑两轮实测

保持拓扑不变，避免同时发送其他实验流量。在 Mininet CLI 执行以下命令，运行前建议打开负载均衡页面。

```text
mininet> py __import__('run_balance').run(net, seed=17, seconds=30)
```

脚本先安装基线路径，再安装均衡路径。每轮启动 10 个 iperf3 服务端（5201–5210）及 10 个客户端，各自以 1～10 Mbps 的目标速率发送 UDP。脚本等待服务端就绪，并排除前四秒以及任一客户端退出后的端口样本。运行期间在页面可看当前轮次与端口统计。如果 Ryu 使用其他 HTTP 端口，可通过 `base_url` 参数指定。建议让发流脚本和 Ryu 运行在同一个 Ubuntu 实例，便于对齐单调时钟。

脚本打印日志目录并将结果保存在 `lab/evidence/load-balance-<UTC 时间>/`。每轮目录包含分配方案、逐流的服务端和客户端 iperf3 JSON、逐流接收速率和丢包率。根目录的 `links.csv` 同时列出每个有向链路的两轮计划百分比、稳定窗口实测均值与样本数。空白表示该方向缺少有效样本。正常结束后，脚本会撤回本次安装的负载均衡流表。

也可以手动用页面按钮安装任一轮路径，再按「流量需求与路径」表中列出的源、目的、速率和端口启动客户端和服务端。同一个服务端口的正反向 TCP 和 UDP 均由相同路径承载，以支持 iperf3 的控制连接及 UDP 握手。

## 选路与计数

- `load_balance.py` 用固定随机种子打乱 20 台主机，配成 10 对，再为每对生成整数速率。基线对每个主机对运行现有的 Dial Dijkstra。
- 均衡方案从大流到小流规划。对当前这条流，把加入后会超过阈值的链路暂时移出图，用 BFS 找源到目的的最短路。按候选阈值从低到高尝试，且阈值下界是已经规划的全网峰值。选好路径后，累加该流在各有向链路的负载。
- 批量贪心结果依赖先前的分配。如果峰值高于基线，均衡方案采用基线。计划容量计算基于 UDP 目标速率。实测端口计数还包括报文头、控制连接和同一端口的其他流量。
- 控制器按源与目的 IPv4、入端口、协议和服务端口匹配规则。负载均衡流表使用优先级 105 及专用 cookie。每批下发后等待 Barrier，拓扑变化时将实验标为失效并撤回本批规则。切换方案会先撤回上一批规则，适用于两轮实验之间切换。
- Ryu 利用 PortStats 的两次 `tx_bytes` 差值得到 Mbps，并按 LLDP 端口映射到有向链路。拥塞链路的接收端可能丢包，即使端口计数看起来接近额定容量，应同时查看 iperf3 的接收速率和丢包率。

`GET /api/load-balance/plan?seed=17` 返回两个方案。向 `POST /api/load-balance` 提交 `{"seed":17,"mode":"baseline"}` 或 `{"seed":17,"mode":"balanced"}` 安装对应规则。通过 `GET /api/load-balance` 获取本轮状态与实测数据，向 `DELETE /api/load-balance?id=<实验 ID>` 提交当前 ID 后撤回该批规则。
